# 编码 CLI 可插拔抽象 — 需求规格（总）

> 版本：v1.0（2026-08-09）。本规格交付他人开发，不含详细开发计划，仅含需求、边界与方向性开发指导。
> 现状事实基线：`docs/analysis/`（00-summary + 5 域分文件，已经多轮核对，可直接引用，无需再次核实）。
> 术语基线：根目录 `CONTEXT.md`（「编码 CLI」「CLI profile」「四态」「历史会话」词条已按本规格决策修订）。

## 1. 背景与目标

slTerminal 当前对 claude（Claude Code CLI）做了 118 项定制优化（盘点见 `docs/analysis/00-summary.md`），其中 54 项硬编码 claude、44 项「通用机制但 claude 触发」。后续需要支持其他编码 CLI（codex、aider 等），先把 claude 定制抽象为高内聚、低耦合、易扩展的可插拔架构。

**目标**：建立「CLI profile」抽象——一个编码 CLI 的完整能力描述与注册单元；claude 迁移为首个 profile；定义「新增 CLI 接入清单」，使未来接入新 CLI 时改动收敛到「一个 profile 文件 + 一行注册 + 可选的后端 provider」。

**非目标（范围外，明确不做）**：

| 范围外项 | 说明 |
|----------|------|
| 第二真实 CLI 的接入与能力分析 | 不分析 codex/aider 等任何具体 CLI 的协议与数据格式 |
| npx/bunx/路径限定调用的 CLI 识别 | 首 token 为 npx/node/路径时无法归因，列为已知限制 |
| 用户自定义命令别名（settings.json 映射） | 一期不做，profile.commands 为内置静态声明 |
| profile 的用户级配置（settings.json 启用/禁用/参数化） | profile 为代码内静态注册 |
| 终端行为适配层（DA1/合帧/resize/OSC 52/Kitty/Ctrl+Enter/flags 0x7/env 注入）的 profile 门控 | 已决策为全局常驻，见 §4-D4 |

## 3. 总体架构

### 3.1 profile 模型（方向性指导，非最终接口）

前端 profile（TypeScript，`src/features/cliProfiles/` 建议落点）：

```ts
/** 编码 CLI Profile —— 一个 CLI 的完整能力描述（身份 + 分域能力，能力可选） */
interface CodingCliProfile {
  id: string;                 // cliId 公共键，如 "claude"
  displayName: string;        // 展示名（hub 面板选择行等），如 "claude"
  commands: string[];         // CLI 识别匹配集：命令行首 token 精确匹配键集
  iconSrc: string;            // 品牌 logo 根绝对路径，如 "/cli-icons/claude.png"
  tabTitle: string;           // OSC 133 C 命中时页签标题，如 "claude"
  capabilities: {
    hooks?: HooksCapability;      // 可选：hooks 注入/事件状态映射/通知分类/用量/配置编辑
    history?: HistoryCapability;  // 可选：历史会话恢复参数
  };
}

interface HooksCapability {
  eventToStatus(event: string, notificationType?: string | null): AgentStatus; // 策略注入
  classifyNotification(payload: AgentEventPayload): "permission" | "error" | "done" | null;
  contextLimit: number;         // claude = 200_000（替代 CLAUDE_CONTEXT_LIMIT）
  restartHint: string;          // 配置保存后提示，claude = "hooks 改动需重启 claude 会话生效"
  hasConfigEditor: boolean;     // 是否出现在 hub 面板选择行（claude = true）
}

interface HistoryCapability {
  supportsFork: boolean;        // claude = true（--fork-session）
  buildResumeCommand(session: AgentHistorySession): string;   // 剪贴板复制用
  buildRestoreInput(session: AgentHistorySession, opts: { fork: boolean }): string; // pty.write 注入用
}
```

后端 profile（Rust）：按域分 trait——`CliHistoryProvider`（scan/delete/validate_session_id）与 `CliHooksProvider`（inject/uninstall/status/context_usage/config_read/config_write），静态注册表以 cliId 为键，claude 为首个实现。注册表形态照前端既有「模块级单例注册表」先例（TabTitleRegistry/CliIconRegistry/SideViewRegistry 等，项目第 6 个注册表单例模式）。

### 3.2 能力域总表（profile 声明 vs 全局常驻）

| 域 | 归属 | 现状来源（analysis 条目） |
|----|------|--------------------------|
| 身份识别（commands/iconSrc/tabTitle） | profile 身份域 | 04-3/4/5/6 |
| 事件→四态映射 / 通知分类 / 用量口径 / 配置保存提示 | profile.hooks（可选） | 04-1/2/14/17、02-25 |
| hooks 注入/卸载/状态/reporter/配置三层读写 | profile.hooks（可选，后端 provider） | 02-1~8、16~24、26 |
| 历史会话 scan/delete/恢复命令 | profile.history（可选，后端 provider） | 03-1~16 |
| 终端行为适配（DA1/合帧/resize/OSC 52/Kitty/Ctrl+Enter/Ctrl+C/flags 0x7/COLORTERM/SLTERM_PANEL_ID） | **全局常驻，不归 profile** | 01-1~4、14、16~19、22、23 |

### 3.3 关键数据流（改造后）

```
① 身份通道（OSC 133，无 hooks 的 CLI 的唯一通道）
shell-integration.ps1 Enter hook → OSC 133 C;<命令行> → useCommandDetection
  → CliProfileRegistry.matchByCommand(命令行)（首 token 解析单点）
  → 命中 profile → 页签标题/🟡/logo + TerminalRegistry.setAgentSession(panelId, { cliId, matchedCommand })

② 事件通道（hooks 能力 CLI）
PTY spawn 注入 SLTERM_PANEL_ID（通用路由键，保留）→ CLI hook 触发 → 该 CLI 的 reporter
  → 信号文件（payload 携 cliId，缺省兼容 "claude"）→ watcher 双通道 → "agent-event" 广播
  → 前端按 panelId 过滤 → profile = registry.get(payload.cliId ?? agentSession?.cliId ?? "claude")
  → profile.hooks.eventToStatus(...) → 页签 emoji + setAgentSession({ sessionId, transcriptPath, status })
  → profile.hooks.classifyNotification(...) → F4 通知调度

③ 历史通道
agent_history_scan()（后端聚合全部已注册 HistoryProvider，条目携 cliId）
  → 前端聚合 UI（当前项目/全部项目两区，行级 CLI logo 区分）
  → 恢复四步编排复用现状，第 4 步注入内容 = profile.history.buildRestoreInput(...)
```

## 4. 决策总表（本次澄清全部结论）

| # | 决策 | 结论 | 理由 |
|---|------|------|------|
| D1 | 规格范围 | 纯架构抽象 + claude 迁移为首个 profile + 接入清单；**不分析其他 CLI** | 控制范围，架构先行 |
| D2 | 架构形态 | **集中 profile 注册表 + 分域能力声明**；领域机制保持现状改 profile 驱动 | 「新增 CLI = 一个 profile 文件」的高内聚目标；不为抽象重写已验证机制 |
| D3 | CLI 识别 | profile 声明 `commands: string[]` 首 token 匹配集；首 token 解析**单点化**（现状 cliIcons.ts:30-33 与 TabTitleRegistry.ts:41-44 两份拷贝统一）；npx/路径限定为已知限制；用户别名一期不做 | 现状机制已验证，最小扩展 |
| D4 | 终端行为适配层 | **全局常驻，不归 profile**；文档从「claude 定制」重新归类为「终端平台能力」 | 机制通用（任何 TUI 受益）、对非 Ink 应用无害；合帧/resize 本就通用受益 |
| D5 | hooks 信号链路 | **通道泛化 + 能力可选**：信号文件目录/watcher/广播/订阅 CLI 无关；payload 增加 cliId（缺省 "claude" 兼容）；注入/reporter/用量/配置为 profile 可选 hooksCapability；无 hooks 的 CLI 走 OSC 133 单通道（matchedCommand-only 会话，现状已支持） | 通道本就 CLI 无关；claude 专属仅在产生侧 |
| D6 | 历史会话域 | **HistoryProvider 接口 + 聚合 UI**；恢复编排四步框架通用，注入命令由 profile 提供；行级 CLI logo 区分 | UI 结构通用，差异仅在数据格式与命令 |
| D7 | hooksConfig 面板 | **hub 面板**：同页单例（id=`hooksConfig-{pageId}` 不变）+ 顶部 CLI 选择行（能力过滤 + logo + 名称 + `params.selectedCli` 随布局持久化）+ 内部切换；侧栏菜单保持单一入口「打开 Hooks 配置」；面板标题已是「Hooks 配置」无需改 | 用户确认的设计；单面板内切换成本最低 |
| D8 | 状态模型 | **四态归一 + 策略注入**（working⚡/attention🟡/done✅/error❌ 不变）；profile.hooks.eventToStatus / classifyNotification；无 hooks 的 CLI 走 OSC 133 双态（🟡/无图标） | 四态已被五处消费（页签/活跃区/历史区/通知/F8），归一成本最低 |
| D9 | 会话模型 | claudeSession → **agentSession + cliId 字段**；每终端同一时刻一个活跃 CLI（OSC 133 C 切换、D 清）；多终端可各跑不同 CLI；行建模默认态保持 attention（🟡） | cliId 是一切 profile 消费的公共键 |
| D10 | 后端抽象 | Rust 侧 profile 注册表 + **命令泛化去 claude 化 + cliId 参数**；无外部消费者不保留旧命令兼容；watcher/信号通道无 cli 参数 | 硬约束 #4 DTO 双边对应；命令面单一 |
| D11 | 命名迁移 | **全面去 claude 化**：类型/字段/文件/目录/命令/广播事件名/用户可见文案/E2E 断言；profile 内部 claude 专属实现保留 claude 命名（如 `profiles/claude/`） | 避免新开发者误以为系统只支持 claude |
| D12 | 验收标准 | ① claude 全部现有行为零回归（L1–L4 全绿）② profile 机制测试 ③ **mock profile 全链路验证**（测试夹具，非真实 CLI）④ test-inventory/CLAUDE.md 同步 | 抽象的正确性靠「第二条 profile 能走通」实证 |
| D13 | 文档结构 | `docs/spec/multi-cli/` 目录：00 总规格 + 01~05 分域 + 06 接入清单 | 分域并行开发/review |

## 7. 风险与执行注意

1. **构建/测试串行纪律**：`npm run build:e2e` 与 `npm run wdio` 必须串行（`npm run e2e` 已 `&&` 保证）；L1 必须 `--test-threads=1`（ConPTY 并发 spawn 死锁 + env 测试污染）。
2. **DTO 双边对应（硬约束 #4）**：后端命令改名/加参必须同步 `src/types/` + `src/ipc/` + `ipc-*-contract.test.ts` 四维契约测试（命令名/参数结构/返回透传/异常传播）。
3. **E2E helper 门控**：改动涉及 E2E helper 时保持 `E2E_ENABLED` 内联字面量形态（rolldown DCE 红线，见 `src/lib/CLAUDE.md`）。
4. **回归基线**：E2E-06（真实 reporter 链路 + C10 契约）是信号链路唯一端到端守卫，改造信号链路时不得削弱；`compute_conpty_flags` 4 条测试锁死 0x7 与本规格无关，勿动。
5. **分阶段建议（方向性，非开发计划）**：建议落地顺序——① profile 注册表 + claude profile 迁移（前端身份/状态域先行）→ ② 后端命令泛化 + cliId → ③ 历史聚合 UI → ④ hub 面板 → ⑤ mock profile 验收。每阶段 AC-1 全绿后再进下一阶段。

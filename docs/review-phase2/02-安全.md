## 2. 新发现问题

### 新发现 1：SEC-01 `paths_match` 字符串回退削弱 shell 白名单保证（P1）

**证据**

- `src-tauri/src/pty/spawn.rs:1059-1062` 对含路径分隔符的 `shell` 调用 `shell::validate_shell_allowlist`。
- `src-tauri/src/pty/shell.rs:105-122` `paths_match` 在 `canonicalize` 失败时回退到字符串归一化比对：
  ```rust
  fn paths_match(program: &str, resolved: &str) -> bool {
      if let (Ok(cp), Ok(cr)) = (std::fs::canonicalize(program), std::fs::canonicalize(resolved)) {
          ...
      }
      let a = normalize_for_compare(program);
      let b = normalize_for_compare(resolved);
      if cfg!(windows) { a.eq_ignore_ascii_case(&b) } else { a == b }
  }
  ```
- `src-tauri/src/pty/shell.rs:98-104` 注释声称“Windows 大小写不敏感文件系统下，归一化后字符串相等的两路径必然指向同一文件”，该论断在 canonicalize 失败场景（应用执行别名、reparse point、特殊 ACL 导致 `CreateProcess` 可执行但文件 API 打开失败）下不成立。

**问题描述**

当 `program` 或 `resolved` 中任意一侧无法被 `std::fs::canonicalize` 解析时，校验从“文件系统真实身份等价”降级为“字符串归一后是否相等”。攻击者若能构造一个不可 canonicalize 的路径对象（如应用执行别名、手工 reparse point），使其归一化字符串与 `which_full_path` 返回的字符串一致，即可让白名单放行一个与真实白名单 shell 不同的文件系统对象。

**利用路径（示例）**

1. 攻击者在 PATH 更靠前的目录放置名为 `pwsh.exe` 的应用执行别名或 reparse point。
2. 用户/项目配置传入完整路径 `C:\BadDir\pwsh.exe`（含分隔符，触发 canonicalize 分支）。
3. `which_full_path("pwsh.exe")` 因 PATH 顺序优先返回 `C:\BadDir\pwsh.exe`。
4. 若该对象 canonicalize 失败，fallback 字符串比对通过，白名单放行。

**修改建议**

1. 在 fallback 分支不再依赖字符串相等。Windows 下对无法 canonicalize 的路径使用 `CreateFileW` + `GetFileInformationByHandleEx` 获取卷序列号与文件索引号，比较两侧文件身份。
2. 若实现成本过高，应至少将 fallback 限制为“两侧均 canonicalize 失败且路径字符串完全相同”的已知安全场景，并在注释中明确登记其为残余风险。
3. 补充 L1 测试：构造 canonicalize 失败但 `which_full_path` 能返回的两个不同文件对象，断言它们被拒绝。

### 新发现 2：SEC-04 nonce 内联在 srcDoc 中，可被 iframe 自身脚本提取（P1）

**证据**

- `src/panels/html/HtmlPanel.tsx:65-71` 将 nonce 直接拼入注入脚本：
  ```ts
  `window.parent.postMessage({type:"slterm_key",nonce:"${nonce}",fingerprint:...},"null")`
  ```
- `src/panels/html/HtmlPanel.tsx:125-135` `handleMessage` 校验：
  ```ts
  if (e.origin !== "null") return;
  if (e.source !== iframeRef.current?.contentWindow) return;
  if (typeof e.data.nonce !== "string" || e.data.nonce !== nonceRef.current) return;
  ```
- 注入脚本随 `srcDoc` 进入 iframe，与待预览 HTML 在同一执行环境。

**问题描述**

`nonce` 的设计意图是防止“iframe 自身内联脚本伪造 `slterm_key` 消息”。但 nonce 作为明文内嵌在 iframe 的 HTML/脚本中，任何在 iframe 内执行的脚本（包括被预览的恶意 HTML 中的脚本）都可以通过读取 DOM 脚本内容、监听事件、或直接查看同一全局作用域来提取 nonce。因此 `e.source` + `e.origin` + nonce 三层校验对 iframe 内部脚本均不形成有效屏障。

当前 `exportContextBindings("global")` 仅包含 `global.closeTab`（默认 `Ctrl+W`），所以实际影响是：恶意 HTML 可自动关闭当前活动页签。若未来 global 上下文增加更高危命令（如调用 IPC 的命令），该绕过会直接升级为任意操作。

**修改建议**

1. **不再依赖 nonce 防御 iframe 内部脚本**：将 HTML 预览视为不信任内容时，应限制 iframe 可触发的命令集合，或要求用户对来自 HTML 预览的全局快捷键二次确认。
2. **使用 MessageChannel 端口**：若需可信信道，可在父窗口创建 `MessageChannel`，将其中一个 `MessagePort` 通过 `iframe` 加载后的 postMessage 传入（需评估 `allow-same-origin` 风险，当前 `sandbox` 设置下不可行）。更简单的方案是仅转发“关闭页签”类低风险命令，并在 UI 层面提示“HTML 预览中的脚本可触发全局快捷键”。
3. 在 `src/panels/CLAUDE.md` 与 `src/panels/html/HtmlPanel.tsx` 顶部注释中明确记录该威胁模型限制。

### 新发现 3：SEC-05 user 层 hooks 写入确认仅为前端门控，后端未强制（P2）

**证据**

- `src/panels/hooksConfig/useHooksConfig.ts:244-250` 仅在 `layer === "user"` 时弹 `confirmDialog`。
- `src-tauri/src/hooks/claude/config.rs:271-295` `config_write_sync` 执行语义校验与写盘，但未校验任何“用户已确认”令牌。
- `capabilities/default.json:47-48` 已放行 `allow-agent-hooks-config-write`。

**问题描述**

user 层 hooks 配置影响所有项目会话且 `command` 字段可执行任意命令，因此 D9 要求二次确认。但确认弹窗仅存在于前端 UI 路径；任何能够调用前端 `writeHooksConfig`（或直接向 Tauri 发起 `agent_hooks_config_write` invoke）的代码都可以绕过该确认。在当前威胁模型下，若主窗口前端上下文被注入（如通过其他 XSS 面），攻击者可无确认地写入 user 层 hooks，进而在后续 Claude Code 事件中执行任意命令。

**修改建议**

1. 若需将确认作为安全边界，后端应要求请求携带一次性用户确认令牌（如 `userConfirmed: bool` + 签名/时间戳），并对该令牌做最小校验（同一进程内可由前端生成，但可阻止无令牌直接调用）。
2. 或在 `src-tauri/src/hooks/claude/config.rs` 的 `config_write_sync` /命令层增加一层显式日志/审计记录，使得绕过确认的行为可追踪。
3. 至少应在模块 CLAUDE.md 中明确说明：user 层确认是 UX 门控而非后端安全边界，真正的保护来自 hooks 语义白名单 + 命令运行时的用户环境权限。

# 性能审查报告

- **审查日期**：2026-08-18
- **审查范围**：slTerminal 当前工作树（不含测试目录）
- **审查方式**：静态代码分析；无运行时采样/火焰图
- **基线版本**：当前工作树 HEAD（未修改代码）

## 1. 热点路径分析

### 1.1 PTY 数据路径

`src-tauri/src/pty/reader.rs` 中的 `reader_loop` 以 `READER_BUF_SIZE = 16384` 的缓冲区从 ConPTY master 循环读取，每次读取成功即通过 `Channel<PtyEvent>::send(PtyEvent::Output { bytes })` 将数据推向前端。虽然 `Channel` 本身做了内部序列化，但数据仍被切分为最多 16 KB 的片段独立发送，跨 Tauri/WebView 的 IPC 调用次数与输出字节数成正比。

前端 `src/panels/terminal/useXterm.ts` 通过 `usePtyOutput` 再做一次帧合并：64 字节以下直接写入，否则启动 2 ms 空闲定时器，最长 16 ms 强制刷新，并用 DEC 2026 同步更新包裹。这意味着**后端已经切小了包，前端再合并**；后端缺乏批处理导致 IPC 头部开销高，且 64 B 阈值对大量小输出（如进度条、日志流）仍偏激进。

`PtySession` 中的 `output_ring` 容量为 256 KB（`RING_BUFFER_CAPACITY = 262144`），每次 `ring_buffer_append` 都要获取 `RwLock` 写锁。高吞吐场景下，reader 线程与 reattach/查询路径在锁上竞争。

### 1.2 渲染管道

`src/workspace/Workspace.tsx` 对所有 `allPages` 都调用 `PageDockview` 渲染，仅通过 `visible={page.pageId === activePageId}` 控制显示/隐藏。Dockview 实例不会被卸载，inactive page 的 DOM 树只是 `display:none`。page 数量多时，React 组件树规模、Zustand 订阅者数量以及 DOM 节点数都会线性增长，内存和重渲染开销显著。

`src/panels/terminal/TerminalPanel.tsx` 订阅了 `useLayout`、`useFontSize` 以及 `TerminalRegistry.subscribe` 的完整事件。只要 terminal registry 中任意会话状态变化，所有 panel 都会收到通知，即使变化与自己无关。

`src/features/navTree/useNavTree.ts` 在每次 `projects`、`rows`、`history.sessions` 或 `query` 变化时，都重新构建整棵导航树模型。历史会话按项目归属使用 O(N×M) 的前缀匹配，且 `historyByProject` 重新计算后对每个项目列表做 `sort`。会话/历史数量大时，每次状态更新都会触发较重的派生计算。

`src/features/explorer/FileTree.tsx` 采用递归渲染且无虚拟化。展开深层大目录时，React 一次性创建大量 `TreeNodeRow`，每个节点都带独立 hover state 和右键菜单逻辑。

### 1.3 文件 watcher

`src-tauri/src/notify/mod.rs` 的 `notify_watch` 创建 `notify-debouncer-full` 的 `FileWatcher`，`RecursiveMode::Recursive` 递归监听项目根目录，默认 300 ms debounce。`fs_read_dir` 仅过滤 `.git`，不排除 `node_modules`、`target`、`.venv` 等大型依赖目录（`src-tauri/src/fs/mod.rs` 注释明确说明不过滤这些目录）。因此大仓库会产生海量事件，即使 debouncer 合并，仍有显著的 CPU、内存和 IPC 压力。

`src-tauri/src/notify/pool.rs` 的 `LruWatcherPool` 容量仅为 5。项目/页面多时，watcher 会频繁被 stop/start，每次重建递归 watcher 都要重新扫描目录树，造成突发开销。

### 1.4 启动与文件 I/O

`src/main.tsx` 的 bootstrap 最多等待 10 秒 Tauri internals，然后串行加载设置、注入 CSS、动态导入 `App.tsx`。`src/App.tsx` 又串行调用多个 store 的 `loadFromDisk` 并恢复 last active page，任何一步失败都被静默吞掉。

`src-tauri/src/state.rs` 的 `set_project_root` 是同步 `#[tauri::command]`，在主线程执行 `dunce::canonicalize`。项目路径涉及网络驱动器或大量符号链接时，会阻塞主线程。

`fs_read_file` 使用 `std::fs::read_to_string` 一次性读入整个文件（`src-tauri/src/fs/mod.rs`）。虽然前端有 10 MB 硬限制和 1 MB 警告，但只要打开大文件，后端就要完整分配内存并传输；CodeMirror 也要把整个文本加载进编辑器状态。

`src-tauri/src/agent_history/claude/scan.rs` 的 `scan_sessions()` 递归列出顶层目录并读取每个 UUID `.jsonl` 文件，每条文件做 512 KB head + 64 KB tail 解析。历史文件多时，扫描是 O(文件数) 的磁盘操作，`useNavTree` 挂载即触发扫描。

## 2. 发现问题

### P0 — 严重

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| P0-1 | Workspace 为每个 page 保留一个 Dockview 实例，inactive page 仅 display:none | `src/workspace/Workspace.tsx` | page 越多，React 树、DOM 节点、Zustand 订阅者越多；内存和重渲染开销线性增长 |
| P0-2 | notify watcher 递归监听且无 node_modules/target 排除 | `src-tauri/src/notify/mod.rs`, `src-tauri/src/fs/mod.rs` | 大仓库产生海量事件，debounce 只能减缓，无法避免高 CPU/内存/IPC |
| P0-3 | `fs_read_file` 一次性读入整个文件，无流式/分片 | `src-tauri/src/fs/mod.rs` | 大文件打开时后端内存峰值高、IPC 包大、前端编辑器卡顿 |

## 3. 关键建议（按优先级）

1. **单 page 渲染 + 卸载 inactive page**：`Workspace` 只渲染当前 active page 的 `PageDockview`，切换时卸载旧实例；对需要保留状态的 page 考虑快照/懒卸载策略，而不是无条件保留所有实例。
2. **watcher 排除大型依赖目录**：在 `notify_watch`/`fs_read_dir` 中增加可配置排除列表（`node_modules`、`target`、`.git`、`.venv` 等），并提升 `LruWatcherPool` 容量或改为按需暂停而非重建。
3. **后端 PTY 输出批处理**：在 `reader_loop` 中引入 1–2 ms 的本地批处理或 4–8 KB 最小发送阈值，将多次小读取合并为一次 `Channel::send`，减少 IPC 次数。
4. **大文件流式/分片读取**：`fs_read_file` 改为分块读取或通过 stream/channel 推送；编辑器大文件采用虚拟化或仅加载可见区域。
5. **异步化 `set_project_root`**：将 canonicalize 放到 `spawn_blocking_task` 中，避免阻塞 Tauri 主线程。
6. **导航树增量计算**：`useNavTree` 对 `tree` 使用稳定缓存/记忆化，历史归属建立索引（Map<projectId, sessions>），避免每次状态变化全量重建。
7. **TerminalPanel 精确订阅**：让 panel 只订阅自身 panelId/sessionId 相关事件，或从 registry 派生更细粒度的 selector。
8. **`useFileTree` 刷新去抖与增量更新**：`file-saved` 事件也加入 debounce；对已知路径的变更只刷新受影响子树，而非递归重建整棵树。

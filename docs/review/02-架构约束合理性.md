## 2. 逐条评估明细

### 约束 #1：前端绝不直接碰 OS/文件/进程；`invoke` 只允许出现在 `src/ipc/`

**现状**：Grep `invoke\s*\(` 在 `src/` 下仅命中 `src/ipc/*`（含 `agentHistory.ts`、`agentHooks.ts`、`hooksConfig.ts`、`fs.ts`、`git.ts`、`notify.ts`、`projects.ts`、`pty.ts`、`settings.ts`、`window.ts`、`dialog.ts`、`notification.ts`、`clipboard.ts`、`shell.ts`、`index.ts`）与契约测试文件。`@tauri-apps/api/core` 引用同样只在这些文件出现。

**合理性**：该约束是项目 IPC 边界的核心护栏。当前功能规模下（pty/fs/git/notify/hooks/history/window/notification 等 10+ 个后端域），单点 invoke 使命令名、payload 结构、错误传播统一受控，价值高。

**适配性**：新增 `agentHistory`/`hooksConfig` 等模块均自然落入 `src/ipc/` 对应文件，无架构空白。

**结论**：保留。

---

### 约束 #2：后端按功能分模块，模块间不互相穿透，共享只经 `state.rs` 的 `AppState`

**现状**：
- 后端模块 `pty`/`fs`/`git`/`notify`/`hooks`/`agent_history`/`settings`/`projects`/`error`/`state` 边界清晰。
- 子模块间依赖 grep（`use crate::`）显示：业务模块主要引用 `crate::error::AppError`、`crate::state::{AppState, validate_path_within_root, ...}`，以及同模块子文件。
- `state.rs` 作为共享状态容器，自然需要持有 `notify::pool::LruWatcherPool`、`pty::spawn::PtyEvent` 等类型，属于容器聚合而非互相穿透。
- `lib.rs` 在 `.setup()` 中直接调用 `hooks::start_signal_watcher` 与 `hooks::reinject_statusline_on_startup`，这是入口聚合层的合理例外。

**合理性**：约束有效。当前实现未出现模块间循环调用或绕过 `AppState` 直接访问对方内部的状态。

**适配性**：`hooks` 与 `agent_history` 引入的 provider 注册表模式（`CliHooksProvider`/`CliHistoryProvider`）完全位于各自模块内部，未破坏模块边界。

**结论**：保留。

---

### 约束 #3：命令统一注册于 `lib.rs` 的 `generate_handler!`；一律返回 `Result<_, AppError>`；阻塞 I/O 用 `spawn_blocking`

**现状**：
- `src-tauri/src/lib.rs:78-112` 的 `generate_handler!` 注册了 33 条命令，包括泛化后的 `agent_hooks_*` 6 条与 `agent_history_*` 3 条。
- 所有命令签名均返回 `Result<_, AppError>`。
- `hooks`/`agent_history` 等含阻塞 I/O 的命令核心均通过 `tokio::task::spawn_blocking` 执行。

**合理性**：统一注册点是排查命令遗漏、审计权限、维护 DTO 契约的关键单点。当前执行良好。

**结论**：保留。

---

### 约束 #4：DTO 双边对应；`src/types/` ↔ Rust 模块 DTO 一一对应；`snake_case` ↔ `camelCase`

**现状**：
- `src/types/agentHistory.ts` 与 `src-tauri/src/agent_history/mod.rs` 的 `AgentHistorySession`/`AgentHistoryTitle` 八字段/两字段精确对应，并有 serde 键集合测试守卫。
- `src/types/agent.ts` 的 `AgentEventPayload` 与 `hooks/signal.rs` 十字段对应，含 `cliId`/`usageSourcePath`/`usedPercentage` 泛化字段。
- `src/types/hooksConfig.ts` 的 `HooksLayer` 已泛化为 `string`，值集由 `profile.capabilities.hooks.configLayers` 声明；后端 `parse_layer` 校验留在 claude provider 内部。

**合理性**：双边对应约束在泛化 CLI 后仍然成立，但语义契约不再只由 DTO 类型承载，而是分散到 profile 能力声明与后端 provider 校验两处。

**适配性**：当前模式对新增 CLI 友好，但约束未说明"字段类型泛化后语义值集如何同步"。`HooksLayer` 的合法值目前由 claude profile 的 `configLayers` 与后端 `parse_layer` 分别维护，存在隐性同步要求。

**结论**：P2 修订——补充"字段类型泛化后，语义值集须在 profile 与后端 provider 同步登记并配合同步测试"。

---

### 约束 #5：面板封闭；Dockview 面板只能是 `panels/` 下注册过的类型；新增类型 = 加目录 + 在 `panelRegistry.ts` 注册

**现状**：
- `src/panelRegistry.ts` 注册 6 种面板：`terminal`/`editor`/`htmlviewer`/`gitshow`/`diff`/`hooksConfig`，`PANEL_TYPES` 作为布局恢复白名单。
- `layoutSerde.ts` 使用 `isValidPanelType` 过滤未知类型。
- `hooksConfig` 面板（`panels/hooksConfig/HooksConfigPanel.tsx`）是 hub 容器：注册为单一面板类型后，内部按选中 CLI profile 的 `capabilities.hooks.configEditor` 分派具体编辑器组件（claude 专属编辑器或未来其他 CLI 编辑器）。
- `ExplorerPanel` 通过 `fileViewerRegistry.resolve(filePath)` 决定文件打开的面板类型，最终仍落入 `panelRegistry` 注册的类型集合。

**合理性**："面板类型必须在 panelRegistry 注册"的机制有效阻止了未经验证的 Dockview 组件进入布局恢复流程。

**适配性**：`hooksConfig` hub 容器 + 分派子编辑器的模式是新增架构形态，原约束只规定"面板类型注册"，未涉及面板内部再分派。当前实现不违规，但约束未覆盖该模式，新开发者可能误以为 hub 内部编辑器也必须是顶层 Dockview 面板类型。

**结论**：P2 修订——补充"hub 容器面板在 `panelRegistry.ts` 注册单一类型后，可经注册表/策略分派子编辑器组件，子编辑器无需单独注册为 Dockview 面板类型"。

---

### 约束 #6：配色单点；颜色定义于 `theme/schemes/<scheme>.ts`，组件经 `theme/colors.ts` facade token 引用，禁止硬编码颜色

**现状**：
- `src/theme/schemes/` 实际仅存 `linear.ts` 一套内置方案，`index.ts` side-effect 注册，`colors.ts` facade 代理导出 34 个 token。
- `overrides.ts` 将方案值注入 dockview/ allotment/ CM6。
- 全局搜索（`: #rrggbb` 形态）仅命中 `src/main.tsx` 启动链 fail-safe 错误页三处色值。
- `FileIcon.tsx` 六色盘与 `NavProjectRow.tsx` 文件夹蓝属于已登记例外（`features/explorer/CLAUDE.md`、`features/navTree/CLAUDE.md` 均明确记录）。

**合理性**：单点机制有效，新增方案只需在 `schemes/` 新增值文件并在 `index.ts` 注册，消费方零改动。当前仅暗黑/Linear 一套方案，与项目定位一致。

**适配性**：约束正文仅笼统说"既定例外登记"，未给出完整例外清单。新开发者面对 `FileIcon`/`NavProjectRow` 的硬编码色容易产生"约束被架空"的误判。

**结论**：P2 修订——在约束正文中列出当前完整例外清单，并规定"新增例外须同步登记于对应模块 CLAUDE.md 与 CONTEXT.md 配色/例外章节"。

---

### 约束 #7：布局单点；操作页面布局只经 `workspace/layoutSerde.ts` 用 Dockview `toJSON/fromJSON` 存取

**现状**：
- `workspace/layoutSerde.ts` 提供 `saveLayout`/`loadLayout`，包含旧格式修补与白名单过滤。
- `PageDockviewHost.tsx` 在 `onDidLayoutChange` 中经 `saveLayout` 写回 `useProjects.updatePageLayout`。
- `App.tsx` 关闭前抢救当前页布局亦调用 `saveLayout(window.__dockviewApi)`。

**合理性**：布局存取单点防止了多处直接调用 Dockview API 导致的序列化格式漂移。

**结论**：保留。

---

### 约束 #8：会话元数据单点；PTY 进程映射仅在 `panels/terminal/TerminalRegistry` 管理，前端会话元数据已合并，面板只订阅不自存

**现状**：
- `TerminalRegistry.ts` 是模块级 `Map<panelId, RegisteredTerminal>`，持有 `sessionId`/`agentSession` 等元数据。
- `TerminalPanel` 订阅 `TerminalRegistry.subscribe` 以响应 `sessionChange`/`register`/`remove`。
- `workspace/pageApis.ts` 管理多页面 Dockview 实例，通过 `pageApiMap` 按 `pageId` 索引；`TerminalRegistry` 仍按全局 `panelId` 索引，两者职责不重叠。
- `App.tsx` 关闭处理遍历 `TerminalRegistry.getAll()` 杀 PTY，符合"单点管理"语义。

**合理性**：多页面工作区下，PTY 会话全局存活（H6），`TerminalRegistry` 作为跨页面索引是必要的。约束未因多页面而失效。

**结论**：保留。

### 约束 #9：平台分支收敛；`#[cfg(windows)]` 只允许出现在 pty 模块等明确处，业务逻辑不撒 cfg

**现状**：
- 业务逻辑中的 `#[cfg(windows)]` 确实集中在 `src-tauri/src/pty/`（`spawn.rs`、`shell.rs`、`conpty_api.rs`、`win_build.rs`）。
- 但 `#[cfg(windows)]` 同时出现在：
  - `state.rs:480,501,619`（符号链接测试）
  - `settings.rs:438`（测试）
  - `fs/mod.rs:586`（测试）
  - `agent_history/claude/ops.rs:429,448,477`（符号链接测试）
  - `lib.rs:137`（`get_windows_build_number` 命令测试）
- 这些均为 `#[cfg(test)]` 内的平台特性测试，而非业务逻辑。

**合理性**：约束的本意是"业务逻辑不撒 cfg"，但当前措辞未区分业务逻辑与测试。随着 Win10/Win11 深度适配（ADR-0004/0005）落地，pty 模块本身已大量依赖 `cfg(windows)`，若按字面执行，测试中的平台分支也会被视为违规。

**适配性**：原约束在当前阶段可操作性差，且与符号链接安全测试等合理需求冲突。

**结论**：P1 修订——明确划分为：
1. 业务逻辑 `#[cfg(windows)]` 仅允许出现在 `pty/`、`conpty_api`/`shell`/`win_build` 等明确平台适配模块；
2. 测试用例中针对平台特性（如符号链接、Windows Job Object、构建号）的 `#[cfg(windows)]` 可豁免，但须在对应模块 CLAUDE.md 说明。

### 约束 #10：权限最小化；Tauri 2 自定义命令默认放行，`capabilities/` 只管插件权限；不追加通配 `*`

**现状**：
- `src-tauri/capabilities/default.json` 仅声明插件权限（`core:default`、`core:window:*`、`opener:default`、`dialog:default`、`clipboard-manager:*`、`notification:default`）。

**合理性**：权限模型与 Tauri 2 行为一致，capabilities 文件聚焦插件权限，无过度授权。

**结论**：保留。

### 约束 #11：测试覆盖；所有改动的代码都需要添加全量自动化测试用例覆盖

**现状**：
- 项目拥有 3282 条测试（L1 615 + L2 2489 + L3 138 + E2E 40），测试覆盖率高。
- `.claude/test-inventory.md` 已建立"既定豁免清单"（DOC-01），列出 9 项不可自动化项目，包括 `reader_loop` I/O 编排、`spawn_conpty_child` Win32 调用、`lib.rs run()`、ActivityBar 拖拽 mock 理想化、真实鼠标转发、真实 OS 按键、HTML postMessage 真实 WebView2 行为、mockcli L4 历史条目等。

**合理性**："所有改动代码全量测试"作为理想目标有价值，但项目实际已经承认并登记了不可自动化部分。约束与项目实践脱节，继续保留会导致"要么违反约束、要么无法登记豁免"的两难。

**适配性**：当前豁免机制没有写入任何硬约束，仅作为 test-inventory 的惯例存在。

**结论**：P1 修订——将约束改为：
"所有改动代码原则上须添加自动化测试覆盖；对于因 Mutex/RwLock/系统调用/真实 WebView2/真实 OS 输入等无法纯函数化或无法模拟的部分，须在 `.claude/test-inventory.md` 既定豁免清单（DOC-01）登记，并注明豁免原因与兜底层级。"

## 2. 崩溃面收敛（unwrap / panic / catch_unwind）

### 2.1 unwrap / expect / panic! / unreachable! 审计

- **Rust 端 `unwrap()` / `expect()` / `panic!()` / `unreachable!()` 总行数**：约 **1009** 行（含测试代码）。
- **生产代码（`#[cfg(test)]` / `mod tests` 之外）**：经逐文件复核，**未发现 `unwrap()` / `expect()` / `panic!()` / `unreachable!()` 调用**。
  - `state.rs`、`pty/spawn.rs`、`pty/reader.rs`、`notify/mod.rs`、`hooks/mod.rs`、`agent_history/**/*.rs` 等关键文件的生产路径均使用 `Result` 传播或 `map_err` 降级。
  - `settings.rs:395` 的 `last_err.expect(...)` 仅位于测试辅助函数 `run_save_with_retry` 内，不进入生产。
- **测试代码**：约 1009 行，全部位于 `#[cfg(test)]` 或单元测试辅助函数内，符合 Rust 测试习惯。

### 2.2 Mutex / RwLock 中毒处理

生产代码中所有 `Mutex::lock()` / `RwLock::read()` / `RwLock::write()` 均通过 `map_err` 将中毒错误转换为 `AppError`，不会直接 panic：

- `src-tauri/src/state.rs:191`：`project_root.write().map_err(...)`
- `src-tauri/src/state.rs:206`：`ring.lock().map_err(...)`
- `src-tauri/src/pty/spawn.rs:1001-1003`：`spawn_lock.lock().map_err(...)`
- `src-tauri/src/notify/mod.rs:190-195`：`wps.lock().map_err(...)`
- `src-tauri/src/pty/spawn.rs:228-230`：`self.inner.lock().map_err(...)`

### 2.3 catch_unwind / 子进程隔离

- 当前代码**未使用 `std::panic::catch_unwind`**。
- Tauri 框架对自定义命令 panic 有默认捕获行为，但 `reader_loop`、`fs-watcher`、`hook-signal-watcher` 等独立线程若 panic，会按 Rust 默认策略 unwinding，导致所在线程终止并污染其持有的锁。
- **子进程隔离**：Windows 下每个 PTY 子进程被放入 Job Object 并设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（`src-tauri/src/pty/spawn.rs:1378-1463`），应用退出时 OS 会兜底杀子进程，孤儿防护有效。

**结论**：生产代码 panic 表面积极小；主要残余风险是独立线程（reader/watcher）panic 后的锁中毒级联，但当前生产路径没有直接 panic 源。

## 3. 竞态与共享状态

### 3.1 后端 `AppState` 锁策略

- `project_root` 为 `RwLock<Option<PathBuf>>`，读锁在命令内短暂持有后立即释放（克隆出 `Option<PathBuf>`）。
- `pty.sessions` 为 `RwLock<HashMap<...>>`，`pty_spawn` 读锁验证、`pty_kill` 写锁移除、`pty_reattach` 读锁查询，均未与 `spawn_lock` 嵌套，无死锁。
- `file_watchers` 为 `Mutex<LruWatcherPool>`，`notify_watch` 采用“持锁检查/释放/创建/再持锁插入”三阶段，已处理并发创建竞态（`src-tauri/src/notify/mod.rs:286-331`）。
- 潜在风险：`set_project_root` 与 `notify_watch` 之间无显式序列化；项目切换过程中创建的 watcher 可能基于旧 root 通过沙箱校验，切换后仍向旧路径发事件。

### 3.2 前端 active pointer 竞态

- `activeTerminal.ts` / `activeEditor.ts` / `activeExplorer.ts` 使用 `createActivePointer`，`clearActive` 仅在 `active === a` 时清除，已处理 `A blur → B focus` 的竞态。
- 各面板的 `actions` 对象通过 `useMemo` + ref 模式保持引用稳定，避免闭包过期。

### 3.3 `TerminalRegistry` 与订阅

- `TerminalRegistry` 是模块级 `Map`，同步 `notify` 所有 listener。由于 JS 单线程，无并发问题。
- 但 `TerminalPanel` 订阅全部事件（`sessionChange`/`register`/`remove`），任何会话变化都会触发该面板重渲染；高频率 hook 事件下可能成为重渲染雪崩的放大器。

## 4. 异常路径与资源回收

### 4.1 PTY 生命周期

- **正常路径**：`pty_spawn` → `reader_loop` → `pty_kill` 移除 session → kill → join reader → drop session → `ClosePseudoConsole`。
- **孤儿防护**：Job Object `KILL_ON_JOB_CLOSE` 是最后一道防线（P1-19）。
- **异常路径**：
  - `pty_kill` 忽略 `child.kill()` 返回值（`src-tauri/src/pty/spawn.rs:1290`）。
  - `handle.join()` 无超时，kill 失败时可能导致 spawn_blocking 任务长期挂起。
  - 前端 `useXterm` cleanup 调用 `pty.kill(...).catch(() => {})` 后移除 `TerminalRegistry`，若 kill 失败而后端 session 仍存在，该 session 会泄漏到应用退出。

### 4.2 窗口关闭资源顺序

- `src/ipc/window.ts:56-70`：`registerCloseHandler` 调用 `event.preventDefault()`，执行回调后 `finally` 中 `destroy()`。
- `src/App.tsx:105-172`：回调内并发 kill PTY（3s 超时）、保存布局、取消 debounce、保存项目数据（3s 超时）、恢复 statusline。
- 风险：回调内 `Promise.race([..., timeout])` 超时后仍会继续执行后续步骤，并立即 `destroy()`；正在进行的 IPC 可能被中断，但资源泄漏由 Job Object 兜底。

### 4.3 持久化损坏恢复

- `settings.rs` / `projects.rs` 均使用原子写入（`NamedTempFile` + `persist`）+ `.bak` 备份。
- 损坏时回退到 `Null` / `"{}"`，无 corruption 标志，调用方无法区分“无数据”与“数据已丢弃”。该问题在 `05-错误处理.md` 中已提出。

## 5. 前端生命周期与 ErrorBoundary

### 5.1 ErrorBoundary 覆盖

- `src/App.tsx:225-247`：顶层 fullscreen ErrorBoundary 包裹整个应用。
- `src/workspace/Workspace.tsx:253`：每个 `PageDockview` 包裹 inline ErrorBoundary，页面级隔离已做到。
- **缺口**：
  - Dockview 内部**单个面板**没有独立 ErrorBoundary；一个面板渲染错误会导致整页 inline ErrorBoundary 触发。
  - `ActivityBar`、`SideBarArea`、`TitleBar`、全局浮层等顶层组件没有独立边界，任一出错会向上抛到 fullscreen ErrorBoundary。

### 5.2 异步任务与定时器

| 位置 | 状态 | 说明 |
|------|------|------|
| `usePtyOutput` idle/max 定时器 | 清理不完整 | 组件卸载时未取消；`flushBuffer` 会跳过已销毁 terminal，但回调仍触发 |
| `useTerminalInstance` `document.fonts.ready` / rAF | 已防护 | `fontsReadyCancelledRef` + `isDisposedRef` 双重检查 |
| `usePtyResize` ResizeObserver / timer | 已清理 | cleanup 中 disconnect + clearTimeout |
| `useAgentStatus` 60s ticker / 双订阅 | 已清理 | `clearInterval` + `unsubscribe` |
| `useAgentHistory` TerminalRegistry 订阅 | 已清理 | `unsubscribe` |
| `useFileTree` fs-event debounce | 已清理 | cleanup 中 clearTimeout + unlisten |
| `registerCloseHandler` / `onFocusChanged` | 已清理 | 返回 unlisten，但 unlisten 是异步 promise，无取消 |

### 5.3 setState after unmount

- React 19 下卸载后 `setState` 不会抛错，但仍可能执行 effect 闭包中的副作用（如 Dockview API 调用、IPC 调用）。
- `useXterm.ts:431-448` 的 `readHistoryTitle` promise 未做卸载守卫，是较明显的漏网点。

## 6. 资源耗尽

| 资源 | 当前限制 | 风险 |
|------|----------|------|
| PTY 会话数 | 无硬上限 | 用户无限制新建终端可耗尽 OS PTY/进程句柄 |
| 文件 watcher 实例 | `LruWatcherPool` max=5 | 容量偏小，频繁切换项目时重建开销大 |
| fs-event / agent-event 队列 | 无背压 | 事件风暴时内存与重渲染堆积 |
| PTY 输出 ring buffer | 256KB/会话 | 有界，安全 |
| 前端 pending buffer | 64KB/终端 | 有界，安全 |
| E2E 文本缓冲 | 1000 行 | 有界，安全 |
| Dockview 实例数 | 与 page 数成正比 | 所有 page 实例保留，仅 display:none，内存线性增长（性能 P0） |

## 9. 建议修复（按优先级）

1. **限制资源无限增长（P0）**
   - 在 `pty_spawn` 增加 `MAX_PTY_SESSIONS` 上限，超限返回 `AppError::Validation` 或 `Pty` 错误。
   - 为 `notify_watch` 增加目录排除列表（`node_modules`、`target`、`.venv`、`.git` 等），或改为非递归监听 + 按需刷新。

2. **补齐 ErrorBoundary 覆盖（P1）**
   - 在 `panelRegistry.ts` 或 `PageDockviewHost.tsx` 中为每个面板类型包裹 `ErrorBoundary variant="inline"`，实现单面板崩溃不影响同页其他面板。
   - 考虑为 `ActivityBar`、`SideBarArea`、`TitleBar` 等顶层组件增加独立降级边界。

3. **强化 PTY 清理的可靠性（P1）**
   - `pty_kill` 检查 `child.kill()` 返回值，失败时尝试 `TerminateProcess`。
   - 对 `reader_handle.join()` 增加超时，避免 kill 失败后永久阻塞。
   - 关闭序列除遍历前端 `TerminalRegistry` 外，增加后端命令枚举并 kill 全部活跃 session。

4. **增加事件背压/限速（P1）**
   - 后端 `emit_fs_event` / `emit("agent-event")` 增加采样或丢弃策略。
   - 前端对 `fs-event` 与 `agent-event` 消费增加节流，超出阈值丢弃旧事件。

5. **修复异步任务泄漏（P1/P2）**
   - `usePtyOutput` 暴露 dispose/cancel，在 `useXterm` cleanup 中调用。
   - `useXterm` 的 `readHistoryTitle` promise 增加 `isDisposedRef` 守卫。
   - `useAgentStatus` 初始扫描引入 generation 机制。

6. **将 `set_project_root` 异步化（P1）**
   - 将 `dunce::canonicalize` 移入 `spawn_blocking`，命令改为 async，避免阻塞 Tauri 主线程。

7. **持久化损坏感知（P1）**
   - `load_projects` / `load_settings` 返回 corruption 标志，启动阶段据此 toast 或日志告警，避免用户数据静默丢失。

# startup（启动维护期协调）

> 在已打开的工作区库上按固定顺序对账恢复事实；未知或未完成材料只阻断启动，不猜测修复。

## 决策与红线

- **固定顺序与短路**：对账顺序固定为 Journal、维护请求／恢复点、关闭意图、快照索引、历史隔离；任一阶段返回 `NeedsAttention` 后不得读取或执行后续阶段，全部安全才返回 `Ready`。原因：后续动作必须建立在前面持久事实已经安全的基础上。边界：数据库打开、高版本与损坏分流仍由外层负责。
- **Journal 世代与未知类型**：只恢复当前 `store_epoch` 的未完成 Journal；旧世代保留原记录并阻断。当前可写世代的未注册 kind 转为 `NeedsAttention`，已是该状态不得重复写；旧世代不得改写。原因：通用协调器不能解释所属领域材料，迟到的旧世代写也不得污染当前事实。
- **恢复终态复核**：恢复器按 kind 注入并执行真实转换；返回 `Ok` 不代表恢复成功，协调器必须重读 Journal 并确认已到合法终态，假成功不得放行。恢复器错误或存储错误直接上抛，不静默继续。边界：本模块不预实现 Document 或 Agent 恢复器。
- **未知材料只阻断**：维护请求、恢复点、快照索引与历史隔离表只要存在记录就必须 `NeedsAttention`；不得根据文件名、状态或记录内容猜测，不自动永久化、清理或删除。关闭意图只读取未完成枚举，任一未完成即阻断，`Completed` 放行，协调器不推进关闭状态。原因：本切片只建立安全存在性闸门，实际材料处理归对应所有者。

## 验收与测试

- 定向测试：`cargo test -p slterm --test lib_tests persistence::startup -- --test-threads=1`。
- 使用临时真实 SQLite 覆盖空库放行、未知 Journal 幂等阻断、旧世代不改写、恢复器终态复核与错误短路、关闭意图过滤、逐表材料存在性及内容不变、固定阶段顺序和后续不查询。
- 崩溃恢复必须有 drop/reopen 证据：提交窗口留下的 Journal 在重开后经注册恢复器完成，再次重开且空注册表时放行；不得只验证内存状态。关闭意图的提交边界使用收到真实提交回执后直接 `process::exit` 的子进程覆盖，重开须核对精确持久阶段与维护分流。

# 验证 Pipeline

## 概述

4 阶段线性流程：并行分散→集中裁决→逐条判定→精确修改。每个阶段有明确的输入/输出/步骤。

```
阶段 1                 阶段 2                阶段 3                阶段 4
并行验证              交叉裁决              逐条核实              修改源文件
─────────            ─────────             ─────────             ─────────
子代理 A → reviewA ↘                       每条声称 ──→ 接受? → 修改源文件
子代理 B → reviewB → 主代理读取全部 ──→             拒绝? → 不修改
子代理 C → reviewC ↗ 识别矛盾 ──→ 裁决    部分接受? → 仅修正确部分
                     输出 ADJUDICATION.md  无法验证? → 标记待定
```

---

## 阶段 1: 并行验证

**目标**: 对每个检索方向，独立验证其全部声称。

**输入**: 结构化检索输出目录（如 `docs/{topic}/D{N}/` 下的 markdown 文件）

**输出**: `review/D{N}/` 下的 review 文件——每个源文件对应一个 review 文件

**步骤**:

1. 统计源文件数量 N，spawn N 个子代理（每个负责一个方向的全部文件）
2. 子代理内部流程:
   - 读取源文件，提取所有带来源引用的声称
   - 对每条声称：WebFetch 来源 URL → WebSearch 确认事实 → 交叉比对同方向其他文件
   - 按 [output-spec.md](output-spec.md) 格式写入 review 文件
   - **只输出发现的错误**，不输出正确信息
3. 子代理必须遵守的约束:
   - 每条声称的验证结论必须有反证来源（URL + 引用）
   - 不能验证的声称标注"无法验证"和原因
   - 同时做内部交叉比对——同方向子文件之间是否有矛盾

**子代理 prompt 核心要素**:
```
你的任务是验证 [方向名称] 方向的检索文件。
- 源文件: [列出所有文件路径]
- 输出: [每个源文件一个 review 文件路径]
- 方法: WebSearch + WebFetch 外部验证 + 内部交叉比对
- 格式: 严格按 output-spec.md 模板
- 规则: 只输出不正确的信息
```

**确定性约束**:
- 子代理数量 = 源文件数量（若 >5 则分批并行，每批 ≤5）
- 每个 review 文件与原文件 1:1 对应

---

## 阶段 2: 交叉裁决

**目标**: 识别不同方向 review 文件之间的矛盾，查权威来源裁决。

**输入**: 全部 review 文件 + 全部源文件

**输出**: `review/ADJUDICATION.md` — 裁决文件

**步骤**:

1. 执行 `cross-check.ts` 的冲突检测算法
2. 对每个冲突，按 [lessons/verification-methods.md](lessons/verification-methods.md) 的优先级查证:
   - 第 1 优先: 官方文档/API 响应
   - 第 2 优先: 源代码/结构化数据端点
   - 第 3 优先: 社区权威来源
3. 裁决结果写入 ADJUDICATION.md，格式:
   ```markdown
   ### 冲突 N: [矛盾描述]
   | 方向 | 声称 |
   |------|------|
   | D1 | ... |
   | D2 | ... |
   **裁决**: [哪方正确 / 双方都错 / 正确说法]
   **依据**: [URL + 证据引用]
   ```
4. 同时标注严重程度(P0/P1/P2)

**确定性约束**:
- 冲突检测用 `cross-check.ts` 的 map 对比算法
- 裁决优先级严格按 [verification-methods.md](lessons/verification-methods.md) 的证据层级

---

## 阶段 3: 逐条核实

**目标**: 对阶段 1 输出的每个 review 文件中的每条错误声称，判定接受/拒绝/部分接受。

**输入**: 全部 review 文件 + ADJUDICATION.md + 源文件

**输出**: verify 文件（`review/verify/{D}-verify.md`）——每条声称的判定结论

**步骤**:

1. 对每个 review 文件的每条声称:
   - 独立验证: WebSearch/WebFetch 确认 review 声称是否成立
   - 对照 ADJUDICATION 裁决
   - 用 [scripts/classify-error.ts](scripts/classify-error.ts) 判定错误类型
2. 每条声称输出一个判定:
   - **正确** → 记录修改行动
   - **部分正确** → 记录仅修改正确部分
   - **不正确** → 记录拒绝原因（review 本身有误）
   - **无法验证** → 记录原因，标记待第二轮
3. 写入 verify 文件，格式:
   ```markdown
   ## 验证结果汇总
   | 类别 | 数量 |
   |------|------|
   | Review 正确，已修正源文件 | N |
   | Review 不正确，未修改 | N |
   | 无法验证 | N |

   ### R{ID}: [描述]
   - **Review 声称**: [原文]
   - **验证结果**: 正确 / 不正确 / 部分正确 / 无法验证
   - **验证证据**: [来源 + 引用]
   - **行动**: [修改了哪里 / 未修改 + 原因]
   ```

**核心原则**: 默认不修改——只有能证实 review 正确时才修改源文件。不确定时不行动。

---

## 阶段 4: 修改源文件

**目标**: 对阶段 3 判定为"正确"和"部分正确"的声称，精确修改源文件。

**输入**: verify 文件的修改清单 + 源文件

**输出**: 修改后的源文件

**步骤**:

1. 按 verify 文件的"行动"列逐条修改
2. 修改规则（参考 [lessons/reviewer-pitfalls.md](lessons/reviewer-pitfalls.md) 的"修改规范"）:
   - 改完一处立即验证上下文不破坏
   - 修改前检查附近行是否与声称一致（源文件可能已被其他修改改变）
   - 删除内容时检查是否影响周围元素（表格截断、标题归属等）
3. 记录修改清单

**确定性约束**:
- 不修改的条目绝不碰源文件
- 修改范围 ≤ verify 文件标记的行号范围

# 错误分类体系（唯一真值）

## 概述

4 种错误类型，每种含症状、典型案例、根因、预防规则。严重程度 P0 > P1 > P2。

本文件是错误体系的唯一定义处——检索方（structured-web-research）的自检清单和验证方（本 skill 阶段 3）的分类判定都以这里为准。案例标注"示例"的均来自历史检索任务，仅作教学参考。

---

## 类型 1: 事实错误

**症状**: 声称的客观数据与权威来源不符——数量、名称、版本号、API 字段名、状态（open/closed）、行为描述。含两个子类：

- **虚构术语**：文中术语/函数名/变量名在声称的来源页面中完全不存在（P0，影响决策）
- **字段混淆**：将不同层级/上下文的相似字段当作同一字段（如 session 级输入字段 ↔ 工具级输出字段；环境变量 ↔ stdin JSON 字段）

**示例（来自历史检索任务）**:
- 声称某终端模拟器支持 `SourcedRcFileForWarp` 函数 → 该仓库是 issues-only，源码未开源，术语在所有引用来源中不存在（虚构）
- 声称 `permission_mode` 取值为 "ask"/"allow" → 实际那是 `permissionDecision` 字段的取值空间；`permission_mode` 的取值是 "default"/"plan"/"acceptEdits"/"bypassPermissions"（混淆）

**根因**: 检索 agent 凭记忆或推测补充了未实际读取的信息；或读取了过时/非权威的第三方总结而非一手文档；或汇总时合并了相似名称但不同上下文的字段。

**预防规则**:
1. 每个术语必须在来源页面中做全文搜索确认存在，再进行声称；禁止从相关概念"类推"出术语
2. 每个数字/状态必须标注检索日期——"截至 YYYY-MM-DD，X 为 Y"
3. API 字段名必须与官方文档/SDK 类型定义逐字匹配，禁止意译
4. 同名/近名字段必须确认属于同一层级、同一上下文才能合并；环境变量名（全大写）和 JSON 字段名（snake_case）不混淆

## 类型 2: 来源无效/不支撑

**症状**: 引用 URL 返回 404/403，或 URL 可访问但其内容不支撑文档中的声称。

**子类型 2a — 死链**: URL 不存在（404）——引用已下架的扩展、已删除的仓库文件等。
**子类型 2b — 内容不支撑**: URL 存在但内容与声称不符——声称某页面描述了 X 功能，实际页面不包含 X。

**示例（来自历史检索任务）**:
- 引用 3 个 VS Code Marketplace 扩展作为参考，全部返回 404
- 声称某 GitHub issue 是 bug，实际标签为 "Feature Request"

**根因**: 检索 agent 未实际访问引用的 URL；或 URL 来自搜索引擎摘要而非直接抓取。

**预防规则**:
1. 每条引用必须 WebFetch 确认内容存在且与声称一致
2. 引用第三方扩展/包时优先用 registry API（npm API、Marketplace API）而非渲染页面
3. URL 路径中的目录分隔符使用前需确认——`docs/architecture/hooks.mdx` vs `docs/hooks-architecture.mdx`
4. GitHub issue 的标签（bug/feature-request/enhancement）需提取并对照声称

## 类型 3: 过时/歪曲

**症状**: 信息在检索时可能正确，但已被后续更新改变；或引用真实存在但内容被严重曲解。

**子类型 3a — 过时**: 声称基于旧版本——已关闭的 bug 标为现存问题、已弃用的 API 标为有效、已更名的产品用旧名。
**子类型 3b — 歪曲**: 引用内容真实但被严重扭曲——声称"完整支持"某功能，实际引用的 MR 已关闭未合并。

**示例（来自历史检索任务）**:
- 7 个 Windows bug 用现在时描述为"已知问题"，实际 6 个已被修复关闭
- 声称某工具 "2026 年 5 月以 AGPL-3.0 开源"，实际其 GitHub 为 issues-only 仓库
- 声称某仓库 "Stars ~14.5k"，实际已到 ~25k（引用了 4 个月前的数据）

**根因**: 检索 agent 未标注信息的时效性；未区分"计划中的功能"和"已实现的功能"；未验证仓库的实际开源状态。

**预防规则**:
1. 所有 issue/bug 引用必须标注当前状态（open/closed）和关闭日期
2. 功能支持声明必须区分"已实现"和"计划/提议中"
3. 开源声明必须确认实际仓库内容可公开访问
4. 关键数据点（stars、版本号）通过直接访问页面确认，不用搜索引擎缓存的摘要
5. 收购/更名等时间线事件需标注确认来源

---

## 类型 4: 内部矛盾

**症状**: 同一批次产出的不同文件对同一事实描述了不同的值；或同一文件内部前后不一致。

**示例（来自历史检索任务）**:
- 文件 A 说配置层级是 `local > project > user`，文件 B 说是 `user > project > local`
- 汇总报告说 hook 事件有 30 个，子报告说 21 个（TypeScript SDK 定义）

**根因**: 不同检索 agent 查阅了不同版本/不同角度的来源；或同一 agent 在不同时间点搜索得到了不同结果；汇总时没有交叉比对。

**预防规则**:
1. 同批次产出完成后必须交叉比对——同一声称在所有文件中是否一致（用 `detect-conflicts.mjs`，不凭记忆）
2. 数字/列表类声称优先以官方 SDK 类型定义为准
3. 汇总报告中的数字必须与子报告可追溯对应
4. 同一文件的概述和详述部分必须自洽——修改一处时检查全文

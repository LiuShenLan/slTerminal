# 审阅者常见失误

## 概述

从实际验证过程中提取的审阅者（review agent）常见失误模式。每条含症状、触发条件、预防措施。严重程度 P0（虚构内容）> P1（概念混淆/字段错位/过时标注缺失）> P2（自相矛盾/虚假精确）。案例标注"示例"的均来自历史检索任务，仅作教学参考。

---

## P0: 虚构内容

**症状**: 审阅者声称某来源中存在某术语/功能/机制，但实际来源中完全不存在。最严重——影响架构决策。

**触发条件**: 审阅者需要描述不公开源码的系统的内部机制（如闭源产品的内部协议、注入方式）。信息缺口 + 压力下，审阅者可能推测补全而非标注"未知"。

**示例（来自历史检索任务）**:
- 声称某终端通过 `ZDOTDIR`/`BASH_ENV` 注入 shell hook——三个变量在其官方文档中零出现

**预防措施**:
1. 对非公开源码系统的内部机制声明，要求逐术语在来源中 grep 确认
2. 不能在来源中逐词确认的机制描述，标注"推测"或"引用来源未直接描述"
3. 闭源产品的内部实现细节默认标注"未经源码验证"

---

## P1-a: 概念混淆

**症状**: 审阅者将两个不同层级/不同上下文的相似字段当作同一字段。

**触发条件**: 两个字段名称相似，但分属不同层级（如 session 级 vs 单次调用级）。

**示例（来自历史检索任务）**:
- `permission_mode`（session 级，取值 "default"/"plan"）被当作 `permissionDecision`（工具级，取值 "allow"/"deny"）论述

**预防措施**:
1. 相同或相似名称的字段，必须确认它们属于同一上下文/层级后才能合并论述
2. 不同层级字段的值空间分别核实，不交叉引用

---

## P1-b: 字段错位

**症状**: 审阅者声称某 API/配置有字段 X，但实际接口定义中不存在。

**触发条件**: 审阅者从多个来源拼凑信息时，将一个来源的字段错误地归属到另一个来源的接口上。

**示例（来自历史检索任务）**:
- 声称 VS Code `RunOptions` 接口有 `instanceLimit` 字段——实际接口仅有 `reevaluateOnRerun` 和 `runOn`

**预防措施**:
1. API 字段声明必须引用官方类型定义/SDK 源码，不能从博客/教程中推断
2. 声称"某接口缺少某字段"时，必须确认该字段在该接口的官方定义中确实存在

---

## P1-c: 数据过时标注缺失

**症状**: 审阅者用现在时描述已关闭/已修复的问题，将其标注为"现存"。

**触发条件**: 审阅者检索时获取了 issue 的标题和内容，但未提取其关闭状态和关闭日期。

**示例（来自历史检索任务）**:
- 7 个 GitHub issue 中 6 个已关闭修复，但审阅者全部用现在时描述为"已知问题"

**预防措施**:
1. 每个引用的 issue/bug 报告必须提取 `state`、`state_reason`、`closed_at` 字段
2. 已关闭的 issue 在描述中必须使用过去时或标注"已修复（YYYY-MM-DD）"

---

## P2-a: 内部自相矛盾

**症状**: 审阅者自己的证据推翻了自己的结论。

**触发条件**: 审阅者先做了结论，然后引用了一个与结论矛盾的来源但没有复核。

**示例（来自历史检索任务）**:
- 审阅者声称某事件"不可阻止"，但引用的官方文档明确说 "blockable: Yes"

**预防措施**:
1. 每条声称写完后，回头对照引用的来源确认一致性
2. 二元属性（是/否、True/False）的声称，直接从来源中提取值，不凭记忆

---

## P2-b: 虚假精确

**症状**: 审阅者声称了具体数字但无来源支撑。

**触发条件**: 审阅者从非官方来源（README、博客）获取了一个数字，将其作为事实陈述，但该数字在原始来源中并不存在。

**示例（来自历史检索任务）**:
- 声称某工具支持"29 种事件类型"——其 npm 页面未提及此数字

**预防措施**:
1. 精确数字（N 种、M 个）必须有直接来源——不能从"看起来有 N 行"推算
2. 无精确来源的数字使用区间或模糊表述（"多种"、"约 20-30 种"）

---

## P3: 截断引用与虚构修饰的判定边界

**症状**: 文档引用来源标题/文本时截断为前缀，或反向地添加了前缀/数字修饰。判定标准易混淆——哪些计错误、哪些不计。

**判定标准（2026-08 检索任务确立）**:
- **截断引用**（引用部分被截断、省略后半）：所引部分逐字正确且不产生误导 → **不计错误**（如 issue 标题 `[DOCS] Missing Documentation for Various Claude Code Features` 被截断，实际全称还有 `(CLI Flags, Slash Commands, & Tools)` 后缀）
- **虚构修饰**（添加了来源中不存在的前缀/数字/字段）：→ **计错误**（虚构术语/数字归因，见 error-taxonomy 类型 1；如 `[FEATURE]` 前缀、`3650` 建议）

**区分方法**: 对照来源页面逐词比对引用边界——差异发生在"引用范围之外"（截断）还是"引用范围之内"（虚构）。

## 修改源文件时的安全约束

见 [edit-discipline.md](edit-discipline.md)——修改规范的唯一真值。核心四条：范围锁定（不"顺便优化"相邻内容）、上下文检查（表格连续/标题归属/列表层级）、术语一致性、修改后自检。
